# 0014. Общие счета: участники и слияние вместо «последняя запись побеждает»

Дата: 2026-08-30
Статус: accepted

## Context

Нужен сценарий «вести общий счёт с человеком»: оба участника добавляют, правят и удаляют операции общего счёта и видят общую аналитику. Модель синхронизации из ADR-0008 для этого не годится: там один файл `numo-sync.json` и правило «последняя запись побеждает» — второе устройство, записав файл, затирает всё, что первое успело добавить.

Заводить бэкенд ради этого мы по-прежнему не хотим (те же доводы, что в ADR-0008: сервер, аккаунты, деньги и ответственность за чужие финансовые данные).

## Decision

**Общей становится не вся база, а отдельные счета.** У счёта появляется флаг «общий». Личные операции остаются только на устройстве владельца — в общую папку уходят исключительно общие счета и операции по ним.

**Каждый участник пишет свой файл.** В общей папке (одна на устройство, настройка `numo.shared.dir`) лежит по файлу на участника: `numo-shared-<memberId>.json`. Своё устройство пишет только свой файл и никогда не трогает чужие — гонки за один файл исчезают как класс.

**Слияние по операциям, а не по файлу.** Данные собираются из своего файла и всех чужих:

- операции объединяются по `id`; при совпадении id побеждает запись с более поздним `updatedAt`, при равенстве — детерминированно по `authorId`;
- удаление — не исчезновение строки, а «надгробие»: `deletedAt` в самой операции. Иначе удаление у одного участника отменялось бы файлом второго, где операция ещё жива;
- общие счета объединяются так же по `id` и `updatedAt`.

**Часы участников не синхронизированы**, и это принимается: `updatedAt` ставит то устройство, которое изменило запись. Для двух-трёх человек, редактирующих разные операции, этого достаточно; настоящие векторные часы или CRDT — избыточная сложность для семейного бюджета.

**Кто есть кто.** Появляется справочник участников (`MemberRows`): id, имя, цвет. Один из них — «я» (`isMe`), его id генерируется при первом запуске и живёт в базе. У операции появляется `authorId` — видно, кто внёс запись.

## Consequences

- Схема БД растёт до версии 9: `updatedAt`, `deletedAt`, `authorId` у операций, `shared` у счетов, новая таблица участников.
- Удаление операции становится мягким: строка остаётся с `deletedAt` и не показывается. Старые надгробия старше 180 дней вычищаются при открытии репозитория.
- Личный сценарий из ADR-0008 (`numo-sync.json`, LWW) остаётся как есть — это по-прежнему синхронизация одного пользователя между своими устройствами. Общие счета живут рядом, по своим правилам.
- Задержка обмена равна задержке облачного клиента: пока Яндекс.Диск не донёс файл, второй участник изменений не видит. Для семейного бюджета приемлемо, для «кто первый занял такси» — нет.
- Конфликт правки одной и той же операции двумя людьми решается в пользу более позднего изменения, без диалога слияния. Потерянная правка не восстанавливается — но и не ломает базу.

## Alternatives considered

- **Свой бэкенд с аккаунтами** — честный шаринг в реальном времени и полный контроль, но ровно то, от чего отказались в ADR-0008.
- **Один общий файл на всех** — заманчиво просто и ровно так же теряет данные при одновременной записи двумя устройствами.
- **CRDT (например, дельта-состояние на счётчиках)** — корректно при любом числе участников и переупорядочивании, но несоразмерно задаче: у семейного бюджета два-три участника и редкие конфликты.
